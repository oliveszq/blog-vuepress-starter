# 控制代码质量的实操方法：持续 + 紧急

---

## 一、先诊断：为什么"控制不住"

```
需求没想清楚 → 边写边改 → 逻辑散落各处 → 改A坏B → 越改越乱 → 失控
     ↑                                                          |
     └──────────────── 恶性循环 ──────────────────────────────────┘
```

**根因只有两个：**
1. **动手太早**：业务没理清就开始写代码
2. **没有边界**：代码没有清晰的职责划分

---

## 二、持续性方法（日常习惯，每天做）

### 🔴 习惯1：写代码前，先写"三句话"

打开 IDE 之前，在注释或文档里写清楚：

```java
/**
 * 做什么：校验用户是否满足中级工程师的申报条件
 * 输入：用户材料列表 + 职称编码
 * 输出：校验结果（通过/不通过+原因）
 */
```

**如果你写不出这三句话，说明你还没想清楚，不要动手。**

### 🔴 习惯2：一个方法只做一件事

```java
// ❌ 失控的写法：一个方法干了三件事
public void process(String data) {
    // 1. 解析JSON
    // 2. 校验业务规则
    // 3. 存数据库
    // 4. 发通知
    // 5. 写日志
}

// ✅ 控制的写法：每件事一个方法
public ApplyResult processApply(String data) {
    ApplyForm form = parseForm(data);
    validateForm(form);
    saveForm(form);
    notifyUser(form);
    logOperation(form);
    return ApplyResult.success();
}
```

**判断标准：一个方法超过 30 行，就该拆了。**

### 🔴 习惯3：改代码前先写测试（哪怕只有一个）

```java
// 改任何业务逻辑之前，先写一个测试锁定当前行为
@Test
public void 初级职称应该包含员级和助理级() {
    List<String> titles = titleService.getTitlesByLevel("JUNIOR");
    assertTrue(titles.contains("技术员"));
    assertTrue(titles.contains("助理工程师"));
    assertEquals(2, titles.size());
}
```

**没有测试的代码，改一行就是赌博。**

### 🔴 习惯4：每天花 10 分钟"回头看"

```
每天下班前：
├── 今天写的代码，有没有重复的？→ 提取公共方法
├── 有没有超过 3 层的 if-else？→ 用卫语句/策略模式替代
├── 命名是不是自己3天后还能看懂？→ 看不懂就改
└── 有没有写了一半的 TODO？→ 记下来，别拖过3天
```

### 🔴 习惯5：业务梳理用"表格法"而非"脑子想"

每次接到需求，先画这张表：

| 维度 | 内容 |
|------|------|
| **谁** | 哪个角色操作？（管理员/申报人/审核人） |
| **做什么** | 核心动作是什么？（创建/修改/审核/驳回） |
| **输入** | 需要哪些参数？哪些必填？ |
| **规则** | 业务校验规则是什么？（如：初级下分员级和助理级） |
| **输出** | 成功后返回什么？失败返回什么？ |
| **异常** | 哪些情况会失败？怎么处理？ |
| **关联** | 影响哪些其他模块？ |

**填不完这张表，就不要写代码。**

### 🔴 习惯6：统一团队的设计规范（写下来）

```
项目规范文档（放 Wiki 或 README）：

1. 命名规范
   - 表名：模块_业务名（如 title_declare_category）
   - 接口：/api/模块/操作（如 /api/title/condition/list）
   - 方法：动词+名词（如 getTitleList，不用 get）

2. 分层规范
   - Controller：只做参数校验和结果包装，不写业务逻辑
   - Service：编排流程，不写复杂判断
   - Domain：核心业务规则写在这里
   - Mapper：只做 CRUD

3. 异常处理
   - 业务异常：抛 BizException，前端展示 message
   - 系统异常：抛 SystemException，前端展示"系统繁忙"

4. 日志规范
   - 入口方法：打 INFO 日志，记录入参
   - 异常：打 ERROR 日志，记录堆栈
   - 关键分支：打 DEBUG 日志
```

## 三、紧急情况方法（赶工期、救火、接手烂代码）

### 🟢 紧急原则1：先止血，再治病

```
紧急需求来了：
├── 第一步：不要重构！不要优化！
├── 第二步：找到最小改动点
├── 第三步：只改必须改的
├── 第四步：加注释标记"临时方案"
└── 第五步：记录技术债，排期还
```

```java
// ✅ 紧急情况下的正确做法
// TODO [技术债 2026-09-20] 这里临时硬编码了级别映射，
// 后续需要改为从配置表读取 —— 张三
public String getLevelName(String code) {
    if ("JUNIOR".equals(code)) return "初级";
    if ("INTERMEDIATE".equals(code)) return "中级";
    return "未知";
}
```

### 🟢 紧急原则2：先跑通主干，再补分支

```java
// ❌ 一上来就处理所有异常
public Result process(Request req) {
    if (req == null) throw ...;
    if (req.getType() == null) throw ...;
    if (req.getData() == null) throw ...;
    // 50行校验...
    // 还没写核心逻辑
}

// ✅ 紧急时先写主干
public Result process(Request req) {
    // 1. 先写核心流程（5分钟跑通）
    Data data = extractData(req);
    Result result = doCoreLogic(data);
    return result;
    
    // 2. 跑通后再补校验和异常处理
}
```

### 🟢 紧急原则3：改别人的代码，只加不改

```
接手一个烂方法，紧急需求要加一个功能：

❌ 危险做法：重写整个方法
✅ 安全做法：

    // 原有逻辑不动
    oldMethod();
    
    // 新逻辑单独加
    newFeatureMethod();  // ← 只加这一个
```

### 🟢 紧急原则4：用"复制-修改"代替"抽象-复用"

```
紧急情况下：
├── 不要搞设计模式
├── 不要搞抽象工厂
├── 不要搞策略模式
├── 直接复制相似的代码，改几行
└── 等不紧急了，再重构提取公共部分
```

### 🟢 紧急原则5：30分钟法则

```
一个问题卡了 30 分钟还没解决：
├── 立刻停下来
├── 写下当前卡在哪里
├── 去找同事/领导说明情况
└── 不要一个人死磕（会越改越乱）
```

### 🟢 紧急原则6：改完必做的 3 件事

```
紧急改完代码后，提交之前：
├── 1. 搜索你改的类名，看有没有其他地方引用
├── 2. 跑一遍主流程（哪怕手动点一遍页面）
└── 3. 在提交记录里写清楚：改了什么、为什么改、影响范围
```

## 五、最核心的一句话

> **持续性靠"想清楚再动手"，紧急时靠"只改必须改的"。**
>
> 代码失控的根源不是技术不行，而是**在没想清楚的时候就开始写代码**。
> 哪怕你只多花 5 分钟画个表格、写三句话注释，代码质量就能提升 50%。
